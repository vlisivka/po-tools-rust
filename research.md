# Дослідження: Формат diff для режиму benchmark в po-tools

## Тема дослідження
Зміна формату виводу режиму `benchmark` у команді `translate` на формат порівняння (diff) між оригінальними (`msgstr`) та перекладеними ШІ повідомленнями.

## Мета
Розробити та проаналізувати варіанти реалізації режиму `benchmark`, які дозволять:
1. Переглядати запропоновані ШІ зміни у зручному diff-переглядачі з підсвіткою синтаксису (особливо для дрібних відмінностей).
2. Легко відкидати небажані зміни шляхом відхилення конкретного `msgstr`.
3. Зручно накладати (інтегрувати) схвалені зміни на оригінальний файл для отримання покращеної локалізації.
4. Відображати метадані тестування (числову оцінку схожості Levenshtein, виявлені помилки валідації) без забруднення самого дифу, щоб вони не заважали накладанню патчу.

---

## Опис варіантів

### Варіант 1: Генерація стандартного Unified Diff (.diff / .patch) безпосередньо в po-tools
У цьому варіанті при запуску `po-tools translate --benchmark file.po` програма порівнює оригінальні повідомлення з перекладеними ШІ та генерує стандартний уніфікований патч (Unified Diff) безпосередньо у `stdout`.

#### Механізм роботи:
1. Програма парсить оригінальний PO файл у список повідомлень `Vec<PoMessage>`.
2. Для кожного перекладеного повідомлення створюється його копія з перекладом ШІ.
3. Програма відстежує номери рядків оригінального файлу (`line_count_orig`) та нового файлу (`line_count_bench`), щоб генерувати правильні заголовки хунків (`@@ -start,len +start,len @@`).
4. Для повідомлень, де переклад змінився, генерується хунк, який містить:
   - Спільний префікс (коментарі, `msgctxt`, `msgid`, `msgid_plural`) як контекст (із пробілом на початку).
   - Оригінальні рядки `msgstr` (із префіксом `-`).
   - Рядки перекладу ШІ (із префіксом `+`).
   - Спільний суфікс (порожній рядок розділювача) як контекст.
5. Метадані (оцінка схожості, помилки валідації) виводяться як коментарі дифу (рядки, що починаються з `#`) безпосередньо **перед** заголовком хунка `@@`. Оскільки вони знаходяться поза межами хунка, стандартні утиліти на кшталт `patch` або `git apply` повністю ігнорують їх при накладанні, але розробник бачить їх у diff-переглядачі.

#### Демонстрація виводу:
```diff
--- a/uk.po
+++ b/uk.po
# Score: 0.8500 | AI: "Зберегти файл"
# Validation: OK
@@ -45,4 +45,4 @@
 #. Scope: ui
 msgid "Save file"
-msgstr "Зберегти"
+msgstr "Зберегти файл"
 
```

#### Переваги:
- **Підсвітка змін**: Будь-який сучасний редактор (VS Code, Vim) або консольна утиліта (наприклад, `delta`, `colordiff`) автоматично підсвічують синтаксис `.diff`/`.patch` файлів, чітко виділяючи змінені символи.
- **Відхилення змін**: Користувач може просто видалити непотрібний хунк із файлу дифу перед його застосуванням.
- **Накладання змін**: Виконується однією стандартною командою: `patch uk.po < changes.diff`.
- **Чистота оригінального файлу**: Оцінки бенчмарку та коментарі ШІ не потраплять в оригінальний `.po` файл, оскільки вони розміщені поза хунками.
- **Автономність**: Не вимагає додавання нових зовнішніх бібліотек до Rust-проєкту.

#### Недоліки:
- Вимагає реалізації логіки розрахунку номерів рядків хунків у коді `po-tools`, що є тривіальним завданням за умови послідовного рендерингу повідомлень.

### Варіант 2: Генерація AI-перекладеного PO файлу (`benchmark.po`) та використання зовнішніх diff-інструментів
Програма генерує валідний PO-файл, де оригінальні `msgstr` замінені на ШІ-переклади, а оцінки схожості додаються як коментарі перекладача (`# Benchmark: Score=...`).

#### Механізм роботи:
1. Програма виводить весь PO-файл, замінюючи `msgstr` на версії від ШІ.
2. Для порівняння та перегляду користувач використовує зовнішню команду:
   ```bash
   git diff --no-index original.po benchmark.po
   ```
3. Для накладання змін використовується вже наявна у `po-tools` команда `merge`:
   ```bash
   po-tools merge original.po benchmark.po > merged.po
   ```

#### Переваги:
- Проста реалізація (потрібно лише змінити вивід `translate_benchmark_message`).
- Можливість редагувати `benchmark.po` у спеціалізованих програмах локалізації (Poedit тощо).

#### Недоліки:
- Коментарі бенчмарку (`# Benchmark: Score=...`) стають частиною тіла повідомлень у PO-файлі. При дифі вони відображатимуться як додані рядки (`+ # Benchmark: ...`), що засмічує diff.
- Накладання змін через `merge` перенесе й ці коментарі в результуючий файл, що потребуватиме їх подальшого очищення.
- Складніший робочий процес (потрібно створювати тимчасовий файл `benchmark.po`, а потім запускати `merge`).

### Варіант 3: Інтерактивний HTML/JSON звіт
Програма виводить результати бенчмарку в JSON, який потім візуалізується через локальну веб-сторінку.

#### Переваги:
- Максимально красива візуалізація.

#### Недоліки:
- Надлишкова складність.
- Важко інтегрувати з консольними конвеєрами та накладати зміни назад на оригінальний файл.

## Рекомендації

Рекомендується реалізувати **Варіант 1 (Генерація стандартного Unified Diff)**. 
Він ідеально відповідає всім вимогам користувача:
1. Забезпечує інтеграцію з будь-якими стандартними утилітами (`patch`, `git apply`, `delta`).
2. Коментарі з метаданими бенчмарку розміщуються як мета-коментарі дифу, завдяки чому вони видимі користувачу, но не впливають на сам патч (ігноруються утилітою `patch`).
3. Реалізація є чистою та не потребує сторонніх бібліотек, оскільки структура PO-файлу дозволяє легко вираховувати межі повідомлень та генерувати дифи лінійно.

### Деталі алгоритму для Варіанта 1:
Координація номерів рядків відбувається за допомогою двох лічильників: `orig_line_no` та `bench_line_no`, які ініціалізуються як `1`.
Для кожного повідомлення:
1. Форматується оригінальне повідомлення `orig_msg` у рядок (`orig_str = format!("{orig_msg}\n")`) та розбивається на рядки.
2. Форматується нове повідомлення `bench_msg` (де `msgstr` замінено на переклад ШІ, але коментарі залишаються оригінальними) у рядок (`bench_str = format!("{bench_msg}\n")`) та розбивається на рядки.
3. Якщо повідомлення не змінилося (оригінальний `msgstr` збігається з версією ШІ) або не перекладалося (було пропущено):
   - Обидва лічильники збільшуються на кількість рядків в `orig_str`.
4. Якщо повідомлення змінилося:
   - Знаходимо індекс першого рядка, де є розбіжність (це завжди початок поля `msgstr`). Позначаємо його як `diff_start`.
   - Рядки від `0` до `diff_start` є спільним префіксом (коментарі, `msgid` тощо). Вони виводяться з пробілом на початку (` `).
   - Рядки оригінального повідомлення від `diff_start` до передостаннього (без врахування розділювача `\n\n`) виводяться з `-`.
   - Рядки нового повідомлення від `diff_start` до передостаннього виводяться з `+`.
   - Останній рядок (розділювач `""`) виводиться як спільний суфікс із пробілом на початку (` `).
   - Перед самим хунком виводяться коментарі бенчмарку: `# Score: ... | Errors: ...`
   - Заголовок хунка записується як: `@@ -{orig_start},{orig_len} +{bench_start},{bench_len} @@`
   - Лічильник `orig_line_no` збільшується на кількість рядків оригінального повідомлення, а `bench_line_no` — на кількість рядків нового повідомлення.
